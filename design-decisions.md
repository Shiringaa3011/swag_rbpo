# Проектные решения безопасности — CampusPass

Цепочка `T-* → SR-* → D-* → будущая проверка` прослеживается ниже для приоритетного набора S03 (`T-01, T-03, T-04, T-05, T-06`). Дополнительно закрыты `T-02` и `T-07` (средний приоритет), так как решение для них дёшево и опирается на тот же механизм.

### D-01. Доверенная идентичность пользователя из контекста аутентификации

**Контекст:** операции регистрации и отмены принимают идентификатор мероприятия из маршрута, но действующий пользователь не должен определяться данными, которые пришёл менять клиент. Без этого участник мог бы выполнить операцию «от имени» другого пользователя, подставив его ID в теле запроса.

**Решение:** сервер определяет действующего пользователя **только** из `HttpContext.User` (claim `NameIdentifier`), заполняемого ASP.NET Core после серверной проверки учётных данных. Конкретный механизм аутентификации (JWT-токен или cookie-сессия ASP.NET Core Identity) на это решение не влияет — важно только то, что `HttpContext.User` формируется сервером из проверенных учётных данных, а не берётся из тела запроса; команда фиксирует конкретный механизм отдельно при настройке аутентификации. Любой `userId`, переданный в теле или query-параметрах запроса регистрации/отмены, игнорируется: DTO этих операций не содержат поля-идентификатора действующего пользователя, а если оно всё же придёт (например, от устаревшего клиента, который его ещё отправляет) — лишнее поле отбрасывается биндингом модели и не участвует в логике.

**Обоснование:** клиент — недоверенная сторона (TB-01 модели угроз). Единственный надёжный источник идентичности — результат серверной проверки учётных данных, а не содержимое запроса. Это устраняет саму возможность указать чужого пользователя, а не просто её маскирует.

**Связанные угрозы:** `T-04`

**Связанные требования:** `SR-04`

**Будущая проверка:**
- **Условие:** участник A аутентифицирован; в системе существует пользователь B с собственным списком регистраций.
- **Действие:** A отправляет `POST /events/{id}/registrations` (или аналогичный запрос отмены), указав в теле/параметрах `userId = B`.
- **Ожидаемый результат:** операция выполняется для A (регистрация создаётся/отменяется у A); список регистраций B не меняется. См. также критерий `SR-04`.

**Ограничения и последствия:** решение требует, чтобы DTO операций над «своими» объектами в принципе не содержали поля-идентификатора действующего пользователя — это дисциплина API-дизайна, которую нужно соблюдать во всех будущих эндпоинтах, иначе регрессия возможна при добавлении нового маршрута.

### D-02. Серверная проверка владения ресурсом перед изменением или просмотром

**Контекст:** организатор может подобрать ID чужого мероприятия и отправить запрос на его изменение/публикацию или на просмотр списка участников; участник может подобрать ID чужой регистрации и отправить запрос на её отмену. Наличие корректного ID само по себе не должно давать право на объект (TB-01).

**Решение:** перед любой мутацией или выдачей чувствительных данных сервис-слой выполняет запрос к PostgreSQL, который сразу ограничен владельцем (например, `SELECT ... FROM events WHERE id = @eventId AND author_id = @currentUserId`), а не «загрузить объект полностью, затем сравнить поле владельца в памяти». Если запрос не вернул строку — это неразличимо для сервиса, не существует ли объект вообще или существует, но принадлежит другому пользователю; в обоих случаях клиенту возвращается `404 Not Found`, без выполнения операции. Для списка участников это два последовательных действия одного метода, а не одна операция: сначала `GetOwnedOrNotFoundAsync` подтверждает владение (SELECT только по `events`, без join на участников) и возвращает `404` при его отсутствии; только после этого, вторым запросом, читается список участников нужного мероприятия. Так список участников чужого мероприятия физически не запрашивается у базы, если первый шаг не подтвердил владение, — а не «запрошен, но скрыт в ответе». Оба шага выполняются из одной точки входа в сервисе, вызываемой из всех затронутых контроллеров, а не продублированной проверкой в каждом хендлере.

**Обоснование:** авторизация не может опираться на то, что клиент «не показывает» чужой объект в UI — API остаётся доступен напрямую (пример ситуации A кейса S04). Сервер — единственное место, где доверенно известны и личность пользователя, и фактический владелец объекта.

**Связанные угрозы:** `T-01`, `T-02`, `T-03`

**Связанные требования:** `SR-01`, `SR-02`, `SR-03`

**Будущая проверка:**
- **Условие:** организатор A — автор мероприятия E; организатор/участник B аутентифицирован и не владеет E (и не владеет регистрацией участника A, где это применимо).
- **Действие:** B отправляет запрос на изменение/публикацию E, на получение списка участников E или на отмену регистрации A — по известному или подобранному ID.
- **Ожидаемый результат:** запрос отклоняется с `404 Not Found`; поля E, список участников и статус регистрации A не меняются. A выполняет то же действие над своими объектами успешно. Критерии — `SR-01`/`SR-02`/`SR-03`.

**Ограничения и последствия:** выбран `404`, а не `403` — ответ не подтверждает, существует ли вообще объект с переданным ID у другого владельца, что не раскрывает постороннему факт существования чужих объектов по подобранным ID; это осознанный компромисс читаемости ошибки ради избежания enumeration чужих ID. Запрос с проверкой владения заменяет отдельное чтение «загрузить → сравнить», поэтому дополнительной стоимости по сравнению с обычным запросом объекта нет.

### D-03. Атомарная проверка и резервирование места при регистрации

**Контекст (исходное предположение и контрпример):** исходно предполагалось, что для соблюдения `SR-05` достаточно обычной проверки в коде приложения: «прочитать `registered_count`, сравнить с `capacity`, если есть место — вставить `Registration` и увеличить счётчик» — то есть два последовательных шага внутри одного HTTP-обработчика. Контрпример: у мероприятия остаётся одно свободное место; два запроса регистрации от разных участников почти одновременно выполняют шаг чтения **до того**, как любой из них успел записать результат. Оба видят «место есть» и оба создают регистрацию — вместимость превышена, хотя каждый из двух запросов по отдельности был корректен и прошёл свою проверку. Последствие: `SR-05` нарушается, а угроза `T-05` реализуется именно потому, что гарантия находилась не там, где проходит реальная конкуренция, — на уровне кода приложения, а не на уровне СУБД, которая одна видит обе параллельные транзакции. Уточнение цепочки: гарантию нужно переносить на операцию, атомарную с точки зрения СУБД, а не разбивать на «прочитать» и «записать» в приложении.

**Решение:** проверка вместимости и резервирование места выполняются одной атомарной операцией на уровне СУБД. Гарантия звучит так: *при конкурентном доступе из нескольких одновременных запросов к одному мероприятию ровно один из них проходит проверку `registered_count < capacity` и получает разрешение на вставку регистрации; остальные параллельные запросы на это же место получают отказ (какой именно запрос окажется «первым» — не специфицируется и не важно для гарантии), независимо от конкретного SQL-синтаксиса.* Для реализации этой гарантии рассмотрены два применимых способа.

| | **Вариант A — условный `UPDATE ... WHERE ... RETURNING`** | **Вариант B — транзакция уровня `Serializable` с retry** |
| --- | --- | --- |
| Механизм | `UPDATE events SET registered_count = registered_count + 1 WHERE id = @eventId AND registered_count < capacity RETURNING registered_count;` — одна строка SQL, которая сама по себе сериализует конкурентов на строке мероприятия (row-level lock держится до конца транзакции). `UPDATE` и последующий `INSERT` в `Registration` выполняются в одной транзакции: если `UPDATE` не вернул строку, `INSERT` не выполняется вовсе; если же `UPDATE` прошёл, но `INSERT` завершился ошибкой (например, конфликтом уникального индекса из `D-04` — см. ниже), транзакция откатывается целиком, и инкремент счётчика не сохраняется. Достаточно обычного уровня изоляции `Read Committed` — сериализацию конкурентов на мероприятии даёт сама блокировка строки внутри `UPDATE`, `Serializable` для этого не требуется. | Транзакция читает `registered_count`, сравнивает с `capacity`, вставляет `Registration` и инкрементирует счётчик — но на уровне изоляции `Serializable`, который обнаруживает конфликт между параллельными транзакциями и завершает одну из них ошибкой сериализации (`40001`), требующей повторного выполнения транзакции приложением. |
| Компромисс | Проще и дешевле (один round-trip, `Read Committed`, без retry-логики), но завязан на конкретный SQL-паттерн «условное обновление + `RETURNING`», который нужно повторять для любой похожей гарантии в проекте. | Не требует нестандартного SQL — выглядит как обычный код «прочитать → проверить → записать», и изоляция сама исключает гонку; но требует retry-цикла в приложении (как минимум одной повторной попытки), более строгого (и дорогого) уровня изоляции и чаще даёт отказы под нагрузкой. |
| Допущения | Работает на любой СУБД с поддержкой условного `UPDATE ... RETURNING` (PostgreSQL — да). | Требует, чтобы приложение корректно обрабатывало `SerializationFailure` и повторяло транзакцию; без retry это не решение, а источник случайных 500-х ошибок под нагрузкой. |

**Выбор:** вариант A — атомарный `UPDATE ... WHERE ... RETURNING` при `Read Committed`. При текущем масштабе (учебные мастер-классы, не тысячи конкурентных регистраций на одно мероприятие) выигрыш от простоты, более низкого уровня изоляции и отсутствия retry-логики перевешивает потерю переносимости SQL-синтаксиса, а сам паттерн достаточно общий, чтобы переиспользовать его в `D-04`.

**Взаимодействие с `D-04`:** `D-03` и `D-04` пишут в одну транзакцию и должны рассматриваться вместе. Пример: два параллельных повторных запроса регистрации от **одного и того же** уже зарегистрированного участника на последнее свободное место. `D-03` пропустит в `UPDATE` ровно один из них (или оба, если место позволяет), но для каждого прошедшего `UPDATE` последующий `INSERT` в `Registration` наткнётся на частичный уникальный индекс `D-04` (`(event_id, user_id) WHERE status='active'`) — второй `INSERT` от того же пользователя завершится ошибкой уникальности, транзакция откатится, и инкремент `registered_count`, сделанный в этой транзакции, автоматически откатится вместе с ней. Итог: счётчик не превышает вместимость даже для повторных запросов одного пользователя.

**Условие пересмотра:** если потребуется переносимость на СУБД без поддержки `UPDATE ... RETURNING`, либо если профилирование покажет, что блокировка строки мероприятия становится узким местом при реальной нагрузке — тогда пересмотреть в пользу варианта B с явным retry, сохранив ту же гарантию.

**Обоснование:** гарантию «число активных регистраций ≤ вместимость» нельзя обеспечить двумя раздельными запросами к БД из приложения — между ними всегда возможен interleaving параллельных транзакций, что и показывает контрпример выше. Перенос гарантии на атомарную операцию СУБД устраняет окно гонки по конструкции, а не по вероятности, независимо от того, какой из двух вариантов выбран.

**Связанные угрозы:** `T-05`

**Связанные требования:** `SR-05`

**Будущая проверка:**
- **Условие:** мероприятие опубликовано, имеет ровно одно свободное место; два разных аутентифицированных участника не зарегистрированы на него.
- **Действие:** отправить от обоих участников запрос регистрации одновременно (параллельно, например из теста с `Task.WhenAll` на два HTTP-вызова) — именно тот сценарий, что описан в контрпримере выше.
- **Ожидаемый результат:** ровно один запрос создаёт регистрацию и получает `200/201`, второй получает отказ (`409 Conflict`) без создания регистрации; итоговое число активных регистраций на мероприятие не превышает вместимость. Критерий — `SR-05`.

**Ограничения и последствия:** снижает возможность батчевой оптимизации регистраций (каждая — отдельная атомарная операция); при очень высокой конкурентной нагрузке на одно мероприятие строка `events` становится точкой последовательного выполнения — для масштаба CampusPass это не критично, но при будущем пересмотре (см. выше) стоит перепроверить.

### D-04. Уникальность активной регистрации на уровне базы данных

**Контекст:** проверка «нет ли уже активной регистрации этого пользователя» перед вставкой новой, выполненная двумя раздельными запросами в приложении, подвержена той же гонке, что и D-03: два почти одновременных запроса от одного пользователя могут оба пройти проверку «регистрации ещё нет» (T-06).

**Решение:** на таблице `Registration` создаётся частичный уникальный индекс, запрещающий более одной активной записи для пары `(EventId, UserId)`:

```sql
CREATE UNIQUE INDEX ux_registration_active_unique
ON registrations (event_id, user_id)
WHERE status = 'active';
```

Приложение по-прежнему выполняет предварительную проверку для быстрого и понятного ответа (`409` с сообщением), но именно индекс — последняя линия защиты: при конфликте вставка завершается ошибкой уникальности на стороне СУБД (в PostgreSQL — код `23505`), которую сервис перехватывает и превращает в тот же `409 Conflict`, не позволяя создать дубликат ни при каком порядке выполнения запросов. Код ошибки СУБД-специфичен и приведён как пример для PostgreSQL; сама гарантия (СУБД физически не допускает вторую активную строку) от конкретного кода не зависит.

**Обоснование:** ограничения целостности, проверяемые в приложении, не дают гарантии при параллельном доступе; СУБД — единственный компонент, видящий все конкурентные транзакции и способный гарантировать уникальность атомарно.

**Связанные угрозы:** `T-06`

**Связанные требования:** `SR-06`

**Будущая проверка:**
- **Условие:** участник уже имеет активную регистрацию на мероприятие E.
- **Действие:** тот же участник отправляет ещё один запрос регистрации на E (в том числе — два параллельных повторных запроса).
- **Ожидаемый результат:** ни один из повторных запросов не создаёт вторую активную регистрацию; участник получает отказ (`409`); число его активных регистраций на E остаётся равным одной, число занятых мест не растёт. Критерий — `SR-06`.

**Ограничения и последствия:** требует, чтобы отмена регистрации физически меняла `status` на не-`active` (а не удаляла строку) — иначе индекс не защитит от «отмена + мгновенная повторная регистрация» в смысле бизнес-истории; это согласуется с текущей моделью (`cancelled` как статус, а не удаление).

### D-05. Фильтрация по состоянию мероприятия при просмотре и регистрации

**Контекст:** мероприятие в состоянии `draft` не должно быть доступно посетителям/участникам, но прямой запрос по известному ID мог бы вернуть его, если сервис не учитывает состояние (T-07).

**Решение:** решение разделяет два разных по смыслу условия, а не одно общее для всех операций:

- **просмотр** мероприятия (получение по ID, попадание в список) — условие `(State = 'published' OR AuthorId = @currentUserId)`: автор видит собственное мероприятие в любом состоянии, включая `draft`; любой другой пользователь видит только `published`;
- **создание регистрации** — условие строго `State = 'published'`, без исключения по автору: черновик не принимает регистраций ни от кого, включая его собственного автора. Регистрация — это действие участника на опубликованное мероприятие по смыслу продукта (раздел 1 `PROJECT.md`); то, что пользователь одновременно является автором мероприятия, не делает его допустимым объектом для регистрации на собственный ещё не опубликованный черновик.

Оба условия применяются на уровне запроса к БД (`WHERE`), а не фильтрацией результата после загрузки в память.

**Обоснование:** свойство должно выполняться независимо от того, пришёл ли запрос из общего списка или по прямому ID — поэтому условие размещается в общем месте построения запроса к мероприятию, а не только в обработчике списка.

**Связанные угрозы:** `T-07`

**Связанные требования:** `SR-07`

**Будущая проверка:**
- **Условие:** существует мероприятие E в состоянии `draft`, известен его ID; его автор — организатор O.
- **Действие:** (1) посетитель или сторонний участник запрашивает E напрямую по ID, через общий список и через запрос регистрации на E; (2) сам O запрашивает E по ID (просмотр) и отдельно — отправляет запрос регистрации на E.
- **Ожидаемый результат:** для постороннего — E не возвращается ни в просмотре, ни в списке, регистрация отклоняется. Для автора O — просмотр E по ID успешен (черновик виден автору), но запрос регистрации на E отклоняется и для O тоже. После публикации (`State = 'published'`) регистрация становится доступна всем, включая O. Критерий — `SR-07`.

**Ограничения и последствия:** существенных ограничений нет. Разные условия для просмотра и регистрации не конфликтуют с `D-02` (который применяется к проверке владения перед мутацией чужого объекта, а не к видимости по состоянию) и не добавляют значимой нагрузки — это обычные предикаты `WHERE` по уже индексированным полям.
